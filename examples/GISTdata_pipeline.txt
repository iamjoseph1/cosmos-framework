GISTdata head-camera action pipeline

Provenance and naming
  GISTdata identifies the GIST-provided original action trajectories.
  Original float32 absolute joint commands are retained byte-for-byte. The head
  RGB and measured proprioception are recordings in Isaac Sim while executing
  those trajectories (red_objects_defaultscene_3cam), not GIST camera recordings.
  No generated, recolored, or otherwise edited videos are used.
  manifest.json records provenance, original action/file hashes and head-video
  hashes. The validator rejects changed commands or videos.
  Preparing this bundle does not execute training or produce trained weights.
  The input report filename is preserved for compatibility with existing data.

Data lives outside the repository, independently of training outputs:
  $HOME/datasets/GISTdata/original_actions/
  $HOME/datasets/GISTdata/head_joint18_original_v1/

Prepared bundle: $HOME/datasets/GISTdata/head_joint18_original_v1
  200 episodes: 100 bowl + 100 mug. Train/validation: 183/17 episodes and
  4758/442 windows. The unsuccessful ycb_mug/data_0071 is retained and tagged.
  Each WAM window conditions on the current head image, task instruction and
  measured 18-D joint state, supervising 32 future commands and head images.
  Units: radians; joint order: manifest.json joint_names; control rate: 20 Hz.
  The initial state prefix is not a robot command. Commands are not normalized.
  Source videos remain byte-identical; training pads 320x240 images to 320x256.

Re-create data in a NEW directory (existing outputs are refused):
  bash examples/prepare_GISTdata_action.sh /path/to/GISTdata /path/to/new_bundle

Validate in an installed Cosmos environment:
  python -m cosmos_framework.scripts.validate_GISTdata_action_data --bundle /path/to/bundle
  Add --tokenizer-folder /path/to/Nano/text_tokenizer to verify tokenized samples.

Training requires the locked Python 3.13 training environment, a converted BASE
Cosmos3-Nano DCP checkpoint and the matched Wan2.2 VAE. The Sim-Transfer checkpoint
cannot initialize this policy. CPU data/config checks do not establish GPU fit.

Prepare the missing base DCP checkpoint (CPU conversion, includes HF download):
  CUDA_VISIBLE_DEVICES="" python -m cosmos_framework.scripts.convert_model_to_dcp --checkpoint-path Cosmos3-Nano -o "$BASE_CHECKPOINT_PATH"

  export GISTDATA_ACTION_BUNDLE="$HOME/datasets/GISTdata/head_joint18_original_v1"
  export BASE_CHECKPOINT_PATH=/path/to/Cosmos3-Nano-DCP
  export WAN_VAE_PATH=/path/to/Wan2.2_VAE.pth
  export OUTPUT_ROOT="$PWD/outputs/train"
  export NPROC_PER_NODE=2
  bash examples/launch_sft_action_policy_GISTdata_nano.sh

W&B logging is online under inrol/rb_xhand_dish_pnp. Set WANDB_ENTITY=inrol;
WANDB_PROJECT can override the recipe project, so keep it rb_xhand_dish_pnp.
The framework logs its resolved config and native loss/optimizer metrics.
The train/val split is retained, but automatic validation is disabled in this
initial recipe; held-out task success is not measured by the training logger.

Current server recipe: complete Edge generation pathway + robot projections
  source .venv/bin/activate
  source outputs/GISTdata_action/train_environment.sh
  python -m cosmos_framework.scripts.prepare_GISTdata_edge_checkpoint --output "$BASE_CHECKPOINT_PATH"
  bash examples/launch_sft_action_policy_GISTdata_edge.sh -- trainer.max_iter=2 trainer.grad_accum_iter=1 checkpoint.save_iter=2 job.name=GISTdata_edge_smoke
  bash examples/launch_sft_action_policy_GISTdata_edge.sh -- job.name=GISTdata_edge_v1

This follows the trainable scope of NVIDIA's DROID-to-Edge post-training guide:
https://developer.nvidia.com/blog/post-train-nvidia-cosmos-3-edge-for-on-device-robot-control/
All 28 generation layers, the final generation norm, generation-specific und-K
cross-attention norms, time_embedder, vae2llm, llm2vae, action2llm, llm2action and
action_modality_embed train. Understanding weights and the VAE stay frozen.
1,423,911,744 parameters train. Fresh action projections use the action recipe's
5x LR multiplier. The 2e-5 base LR, batch 8, 600-step schedule, 256 resolution and
20-Hz 18-D embodiment are GISTdata adaptation defaults, not official tuning for
this dataset or a reproduction of the large-scale DROID run.

The server selects the idle physical Blackwell GPU 1 by UUID and one rank.
Configuration: examples/toml/sft_config/action_policy_GISTdata_edge.toml.
Model/processor revision is pinned together in utils/GISTdata_edge_contract.py.
The preparation command verifies provenance before reusing a converted DCP and
refuses to overwrite partial or unmatched checkpoints. It downloads the pinned
HF snapshot and runs conversion on CPU, without taking another GPU.
If Xet transfer stalls, prefix the preparation command with HF_HUB_DISABLE_XET=1
to use the supported HTTP download path. Keep the cache for resume. The configured
server environment also adds the existing pinned uv and CUDA 12.8 binaries to PATH,
which native processor/checkpoint helpers need in noninteractive SSH sessions.
The Edge launcher validates all original trajectories and Edge-tokenized samples
before starting torchrun. It refuses a Nano or unmatched base checkpoint.
The data bundle, original actions, state prefix, 32-action/33-frame horizon and
joint order are reused. W&B stays online in inrol/rb_xhand_dish_pnp.

Edge hyperparameters: optimizer.lr=2e-5 (action projections=1e-4), max_iter=600,
grad_accum_iter=8, warm_up_steps=[20], cycle_lengths=[600], save_iter=50.
Effective batch = 1 window/rank x 1 rank x 8 accumulations = 8 windows.
Keep cycle_lengths aligned with max_iter. The loader/dryrun now rejects finite
lambda schedules that end before the run's requested optimizer-step horizon.
To resume, keep OUTPUT_ROOT and job.name unchanged; the latest model, optimizer,
scheduler progress and trainer state are loaded automatically. The configured
schedule is evaluated at the restored step, so extending its length takes effect
without resetting optimizer progress. Earlier learning-rate history is retained.
Optional two-GPU FSDP: explicitly select two healthy GPU UUIDs, set
NPROC_PER_NODE=2, and pass trainer.grad_accum_iter=4 to keep effective batch 8.
For local inference, export the trained Edge model with its processor and vision
encoder and provide the matched VAE locally. Never copy only the trained layers.
BF16 inference on the RTX 5070 Ti 16GB still needs a real peak-memory/latency check;
the release's approx. 8.5-GiB weight files do not include runtime allocations.

Alternative Nano recipe: two-GPU last-six-generation-layer tuning
  source .venv/bin/activate
  source outputs/GISTdata_action/train_environment.sh
  bash examples/launch_sft_action_policy_GISTdata_nano_last6.sh -- trainer.max_iter=2 trainer.grad_accum_iter=1 checkpoint.save_iter=2 job.name=GISTdata_last6_smoke
  bash examples/launch_sft_action_policy_GISTdata_nano_last6.sh -- job.name=GISTdata_last6_v1

The server environment selects physical GPUs 1 and 3 by UUID. The dedicated
launcher requires two distinct visible devices and always launches two ranks.
The last6 experiment trains generation attention, MLP and normalization weights
in layers 30-35 (zero-based), plus the same video/action projections as heads.
Understanding weights and generation layers 0-29 remain frozen. The native
optimizer selects 1,195,061,056 parameters, including with activation checkpoint
wrappers present. VAE, joint order, raw commands and WAM conditioning are unchanged.
Hyperparameters: examples/toml/sft_config/action_policy_GISTdata_nano_last6.toml.
Parameter selection: action_policy_GISTdata_nano_last6.py in the experiment folder.
FP32 parameter/gradient/Adam memory has an estimated 34.94-GiB lower bound per
rank; activations, VAE, unsharded buffers and CUDA allocations require more.
Actual model GPU fit is not established by CPU scope/config checks. Run the
two-step smoke after converting the base checkpoint before the main training.

Alternative single-GPU projection-only option:
  export SFT_TOML_FILE=examples/toml/sft_config/action_policy_GISTdata_nano_heads.toml
  export NPROC_PER_NODE=1
  export CUDA_VISIBLE_DEVICES=<UUID-of-an-idle-Blackwell-GPU>
  bash examples/launch_sft_action_policy_GISTdata_nano.sh -- trainer.max_iter=2 trainer.grad_accum_iter=1 checkpoint.save_iter=2 job.name=GISTdata_heads_smoke
  bash examples/launch_sft_action_policy_GISTdata_nano.sh -- job.name=GISTdata_heads_v1

The heads recipe freezes both MoT language pathways and trains time_embedder,
vae2llm, llm2vae, action2llm, llm2action and action_modality_embed. Future video
and absolute joint targets remain joint WAM supervision. The native FP32
parameter storage and BF16 compute policy are retained.
This smaller parameter scope is a separate option, not full generation-tower SFT.
Full generation-tower SFT uses action_policy_GISTdata_nano.toml. Its language
weights plus generation gradients/Adam states alone need about 134 GiB before
activations, VAE and other heads, so a single 96-GB GPU cannot fit that recipe.
Use sufficiently free GPUs with FSDP for that recipe; smoke-test before a full run.

Nano-last6 hyperparameters (edit the selected TOML; CLI Hydra overrides apply last):
  [optimizer].lr = 2e-5; [scheduler].f_max = [1.0] makes this the peak LR.
  [trainer].max_iter = 200, grad_accum_iter = 4, logging_iter = 1 (last6).
  [scheduler].cycle_lengths = [200], warm_up_steps = [20].
  [checkpoint].save_iter = 50.
  [dataloader_train].max_samples_per_batch = 1 (per rank).
  [model.activation_checkpointing].mode = "full".
  Effective batch: samples per microbatch x GPU count x grad_accum_iter.
  With two GPUs, the current packing cap and last6 accumulation, effective batch
  = 8 windows. The single-GPU heads recipe uses grad_accum_iter=8 instead.
  Keep scheduler.cycle_lengths aligned with trainer.max_iter when extending a run.
  Resolution/domain/VAE duration live in the experiment Python files. Changing
  the 32-step horizon requires rebuilding data and matching the VAE duration;
  changing the TOML optimizer settings does not require data preparation again.

Validate configuration without starting training or loading model weights:
  python -m cosmos_framework.scripts.train --sft-toml=examples/toml/sft_config/action_policy_GISTdata_nano_last6.toml --dryrun

Start with a bounded GPU smoke; fit and convergence have not been measured:
  bash examples/launch_sft_action_policy_GISTdata_nano.sh -- trainer.max_iter=2 trainer.grad_accum_iter=1 checkpoint.save_iter=2 job.name=GISTdata_smoke

The default recipe holds out validation episodes. The dataset factory supports
split=all if deliberately training on all 200 episodes without a held-out set.

After training, predict commands and future video from CURRENT inputs only:
  python -m cosmos_framework.scripts.infer_GISTdata_actions --image /path/to/current_head.png --proprioception /path/to/current_joint_angles.json --instruction "Using your right arm and right hand, pick up the red mug and place it at the designated drop-off position on the table." --checkpoint-path /path/to/run/checkpoints/iter_000000200 --config-file /path/to/run/config.yaml --output /path/to/new_prediction

Outputs: predicted_actions.npz, predicted_actions.json (32 x 18 absolute targets),
predicted_future.mp4 and request.json. Commands are never sent to a robot.
Use --dry-run without checkpoint arguments to inspect inputs and condition masks.

Code and configuration belong in Git. Original datasets and prepared bundles
are transferred separately into $HOME/datasets/GISTdata/. Training checkpoints
and logs stay under the repository's ignored outputs/train/ directory.
On the configured server, source outputs/GISTdata_action/train_environment.sh
from the repository root after activating .venv; this file points to the external
dataset directory and selects the full-generation Edge recipe. Historical validation
and transfer reports remain under outputs/GISTdata_action/.

Three-camera Edge experiment (600 optimizer steps)
------------------------------------------------
  python -m cosmos_framework.scripts.prepare_GISTdata_action_data --source /path/to/GIST_original_root --output /path/to/new/threecam_joint18_original_v1 --camera-mode threecam
  python -m cosmos_framework.scripts.validate_GISTdata_action_data --bundle /path/to/new/threecam_joint18_original_v1 --tokenizer-folder /path/to/pinned/Edge/snapshot --tokenizer-model edge

The portable bundle retains the original head.mp4, left_wrist.mp4 and
right_wrist.mp4 bytes. Preparation checks every RGB frame timestamp against
the 20-Hz observation clock, checks dimensions and hashes all 600 RGB files.
Depth is not an input. The loader composes simultaneous frames using native
compose_multiview: head on top at 320x240, left wrist bottom left at 160x120,
right wrist bottom right at 160x120 (320x360 canvas). No camera is dropped or
cropped. Native resolution-256 transforms then resize the complete canvas
with preserved aspect ratio and reflection padding. Camera layout text is
included in the structured prompt. Deployment must use the SAME composition
and layout metadata; the original head-only inference CLI assumes one head
image and is not a direct three-camera inference entry point.

Camera images and measured joints are Isaac Sim observations while executing
original GIST commands, rather than original GIST sensor images. Commands stay
byte-identical 18-D absolute right-arm (6) + right-hand (12) joint targets.
All 200 episodes are packaged: training 183 / validation 17, matching the
head-only grouped split exactly; windows 4758 / 442. The one unsuccessful
original demonstration is retained and tagged, as in the head-only bundle.

For training on the configured remote server:
  source .venv/bin/activate
  source outputs/GISTdata_action/train_environment_threecam.sh
  bash examples/launch_sft_action_policy_GISTdata_edge_threecam.sh

New recipe: examples/toml/sft_config/action_policy_GISTdata_edge_threecam.toml.
600 steps and scheduler cycle [600], accumulation 8, one GPU, per-GPU batch 1,
LR 2e-5 (fresh action heads 1e-4), warmup 20, BF16 and full activation
checkpointing. All 28 Edge generation layers plus robot projections train;
understanding and VAE remain frozen. Effective batch 8 gives 4800 sampled
training windows, approximately 1.009 passes over 4758 training windows.
The streaming loader shuffles episode blocks; this is an approximate epoch
count, not a claim of visiting every window exactly once.

Initialize from the same pinned released Edge base, with a fresh three-camera
job group/name; the head-only model and its optimizer state are not resumed.
The old head run's first 200 steps used its original 200-step scheduler before
it was extended; this new experiment uses a 600-step scheduler from step 0.
Checkpoints every 200 steps (200,400,600) use about 72 GiB instead of about
288 GiB at every 50 steps, preserving existing results on the shared volume.
The configured server uses physical Blackwell GPU 1 and logs a separate run in
https://wandb.ai/inrol/rb_xhand_dish_pnp . Source train_environment_head.sh to
restore the previous head-only environment after the server switch.
